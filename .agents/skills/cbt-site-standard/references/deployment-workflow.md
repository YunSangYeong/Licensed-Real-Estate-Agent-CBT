# 이전 전기기능사 배포 방식 재현 — v1.4.0

## 실제로 확인한 근거

원본 앱 고정 커밋 `b9a682ccff1b460334b78d5bfad9375b7ec4fbb6`의 `.github/workflows/pages.yml`과 README를 읽었다.

- workflow `Test and deploy GitHub Pages`는 main push, pull_request, workflow_dispatch를 받는다.
- validate는 npm ci → 단위 검사 → Chromium 설치 → 프로덕션 빌드 및 PC/모바일 브라우저 검사를 수행한다.
- PR은 검증만 하며, main push는 검증 성공 후 Pages 아티팩트 업로드와 deploy로 이어진다.
- README의 최초 실행 기록 `39135408126`은 validate 성공 후 Pages 최초 설정이 없어 configure-pages에서 404로 실패한 사례다. 사용자가 최초 설정을 마무리하는 지점이다.
- 기준 명세에는 이후 앱 커밋의 성공 실행 `39256284152`가 기록되어 있다. 이는 기존 저장소의 기록이며 이번 작업에서 API로 재확인하거나 새 배포를 실행한 증거가 아니다.
- Git 이력 `69544ee`에서 v1.3.0의 사용자 전담 배포 정책이 도입됐고, `9ed9714`의 v1.3.1은 이를 유지했다. v1.4.0은 그 책임 분리를 대체한다. 앱 코드 기준은 그대로다.

즉, 재현할 방식은 **에이전트 구현·검증·Git 반영 → main push로 자동 검증·배포 → 사용자 권한이 필요한 최초 설정·승인만 지원**이다. 사용자가 PR 작성부터 병합·Actions 실행까지 모두 하는 흐름을 기본으로 삼지 않는다. GitHub 정책과 현재 권한에 따라 같은 성공 결과를 보장하지는 않는다.

## 다음 프로젝트의 실행 순서

1. 사용자의 배포 요청, 대상 자격증/저장소/브랜치를 확인한다. 이 스킬을 읽거나 복사하는 행위만으로 공개 게시를 허용받은 것은 아니다. 새 프로젝트 요청 양식은 배포 요청을 명시한다. 배포 금지·수동 전용·수정 제외 지시를 우선한다.
2. 로컬에서 구현·설치·단위 검사·PC/모바일 검사·프로덕션 빌드를 끝내고 코드·자료·문항 수·실제 검수 범위를 검토한다. 이 로컬 개발 단계에서 실패한 검사를 고치고 다시 실행하는 것은 배포 재시도가 아니다.
3. 배포를 시작하기 전에 기존 자동 트리거·원격 변경·권한·Pages Source와 필수 접근 상태를 필요한 범위에서 확인한다. main push 자체가 배포 시작임을 고려한다. 여기서 권한/인증/네트워크 거부나 사용자 조치 필요가 나오면 **즉시 중단하고 아래 사용자 마무리 절차로 넘긴다.** 다른 도구·다른 경로·push 자동 실행으로 우회하지 않는다.
4. 배포 요청과 접근이 유효하면 에이전트가 정상적인 Git 반영을 진행한다. 새 프로젝트는 아래 조건을 만족하는 원본 workflow 구조를 재사용한다. 기존 보호 브랜치가 PR/사람 승인을 요구하면 가능한 준비까지 처리하고 그 승인만 안내한다. force push나 보호 정책 우회는 하지 않는다.
5. main push가 시작한 **첫 실행 하나**를 추적한다. 같은 커밋을 수동 실행으로 또 배포하지 않는다. 기존 설정상 수동 실행이 필요한 경우에는 자동 실행이 없음을 확인한 뒤 수동 경로 하나만 사용한다.
6. 최초 실행이 성공하면 정확한 커밋·validate/deploy 결과·게시 URL을 보고하고 접근 가능한 공개 화면과 핵심 동작을 확인한다. 정상 진행 중의 상태 읽기는 재배포가 아니다. 상태 읽기 자체가 거부되면 반복하지 않고 미확인으로 보고한다.
7. 첫 실패 또는 사용자 승인이 필요한 지점에서는 에이전트의 배포 진행을 중단한다. 사용자가 직접 마무리한다. 나중에 사용자가 다시 실행을 명시적으로 요청한 경우에만 새로운 1회 시도를 진행할 수 있다.

## 재사용 workflow 조건

기본 출발점은 고정 앱 커밋의 `.github/workflows/pages.yml`이다. 실제 workflow를 복사·조정하는 것은 새 대상 저장소의 구현/배포 작업에서 수행하며 이 표준 문서 변경만으로 기존 workflow를 수정하지 않는다.

- main push: validate 성공 → Pages 아티팩트 업로드 → deploy.
- pull_request: validate만 수행, Pages 게시 없음.
- workflow_dispatch: 필요할 때 하나의 대체 진입점으로만 사용. 이미 push 실행이 있으면 추가 실행하지 않음.
- deploy는 `needs: validate`, main 제한, PR 제외 조건을 둔다. 쓰기 권한은 deploy job의 `pages: write`, `id-token: write`로 한정하고 상위 contents는 read로 둔다.
- 기존 Pages 설정과 정책을 존중한다. 불필요한 토큰·관리자 권한·새 배포 플랫폼을 요구하지 않는다.
- 자동 재시도·재귀 workflow·실패 뒤 다른 배포 경로를 넣지 않는다. 첫 실패 뒤 에이전트가 수정 커밋을 main에 더 푸시해서 재배포를 시작하지 않는다.
- 사용자가 수동 전용을 명시한 프로젝트는 그 지시를 우선해 push 배포를 활성화하지 않는다.

## 사용자 마무리는 필요한 한 동작씩

첫 차단 때는 아래 네 항목만 간단히 설명한다.

1. 어느 단계에서 막혔는지: 사전 확인 / validate / configure-pages / deploy / 환경 승인 / 상태 조회.
2. 실제 오류와 현재 상태: 예를 들어 API Forbidden, Pages 조회 404, 승인 대기. 최초 확인 거부라면 workflow는 아직 실행하지 않았다고 구별한다.
3. 재시도하지 않았다는 사실과 배포 성공/미완료/미확인 상태.
4. 사용자가 지금 해야 할 최소 동작 하나. 예를 들어 최초 설정이 필요한 경우 저장소 Settings → Pages → Source: GitHub Actions 선택만 먼저 안내한다. 환경 승인이면 해당 실행의 github-pages 승인만 안내한다. 그다음 사용자 응답에 맞춰 다음 동작을 안내한다.

링크만 던지거나 PR→병합→Actions 전체를 한꺼번에 숙제로 주지 않는다. 사용자 직접 마무리를 요청받았다고 에이전트가 재실행하거나, 사용자가 설정을 바꿨을 것이라고 추정해 자동으로 다시 시도하지 않는다. 이미 배포된 다른 프로젝트는 건드리지 않는다.

## 문서·스킬 변경만 하는 이번 같은 작업

앱·문항·기존 workflow는 유지한다. main push가 배포되는 저장소이므로 모든 관련 트리거를 확인한 뒤 지원되는 `[skip ci]` 등으로 문서 커밋의 Actions 실행을 생략한다. 안전하게 생략할 수 없으면 배포되지 않는 브랜치에 저장한다. CI/앱 테스트/배포를 실행하지 않았으면 그대로 보고한다. 문서와 참조·JSON·배포 정책 간 일관성만 검사한다. 이전 버전 문서는 역사로 보존하고 v1.4.0 지침과 혼동하지 않게 표시한다.
